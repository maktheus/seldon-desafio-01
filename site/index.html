    Mini-aula 01 · Controle de versão

    Git não é só salvar código. É colaborar.

    Vamos usar princípios de Git Flow em uma versão simples, adequada ao início do projeto: main estável, develop para integração e feature/* para tarefas. Release e hotfix entram quando houver necessidade real.

    main

    Base estável. Nada de commits diretos.

    02

    03

    feature

    Uma tarefa por branch, criada a partir de develop.

    feature/readme
    04

    PR → develop
    05

    Exercício guiado

    O líder cria o repositório. Cada integrante abre uma branch para sua primeira contribuição: documentação, esqueleto de módulo ou teste. O líder revisa o PR, sem fazer tudo sozinho.

    Regra de ouro: nenhuma mudança entra em main sem revisão. Documentem a estratégia de branches no README.
    git switch develop git pull origin develop git switch -c feature/estrutura-inicial # Faça uma mudança pequena e verificável git add . git commit -m "docs: define arquitetura inicial" git push -u origin feature/estrutura-inicial # No GitHub: abrir PR para develop
    Mini-aula 02 · Qualidade automatizada

    CI valida cada mudança. CD prepara entregas.

    CI (integração contínua) executa verificações a cada Pull Request. CD pode significar entrega contínua ou implantação contínua; nesta fase, basta gerar um artefato verificável, sem publicação automática em produção.

    GATE 01

    Build

    O projeto Android precisa compilar. Se ainda não existir app, iniciem com validação de estrutura e documentação, deixando a evolução explícita.

    GATE 02

    Testes

    Comecem com pelo menos um teste automatizado significativo. Depois evoluam para testes de integração e instrumentados.

    GATE 03

    Relatório

    O pipeline mostra sucesso ou falha, preserva logs e, quando aplicável, publica APK ou relatórios como artefatos.

    Exemplo de pipeline Android

    Crie .github/workflows/ci.yml. O exemplo pressupõe um projeto Android com Gradle Wrapper já configurado e testes unitários disponíveis.

    Se a equipe ainda não tiver um projeto Android compilável, não marque a atividade como concluída: configure primeiro o esqueleto mínimo ou documente o bloqueio.
    name: Android CI on: pull_request: branches: [develop, main] push: branches: [develop] jobs: verify: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-java@v4 with: distribution: temurin java-version: '17' - uses: gradle/actions/setup-gradle@v4 - run: chmod +x gradlew - run: ./gradlew assembleDebug testDebugUnitTest

    O QA não trabalha sozinho

    O QA propõe cenários, critérios de aceitação e evidências. Backend e Frontend também escrevem testes. Todos são responsáveis por não quebrar a integração.

    Backend

    Regras de negócio, interfaces, serviços, persistência e testes unitários.

    Frontend

    Fluxos Android, Compose, estados da UI, acessibilidade e testes de interface.

    QA

    Plano de testes, casos críticos, automação, defeitos e qualidade do pipeline.

    Como será avaliado?

    Problema e requisitos 20% · arquitetura e justificativa 25% · Git e colaboração 20% · CI e testes 25% · apresentação e evidências 10%.

    Rubrica sugerida para orientar a atividade; a coordenação pode ajustá-la.

    GitHub: o líder cria o repositório, convida todos os integrantes e adiciona o orientador como colaborador. Solicite à coordenação o username correto do orientador antes de enviar o convite. Na entrega, compartilhe o link do repositório, um PR revisado e o resultado do GitHub Actions.
    Como funciona a apresentação: um único representante apresenta o resultado do time. Para que o trabalho de todos fique visível, o README (seção Contribuições) deve listar, para cada integrante, o que foi feito, com links para commits, issues ou Pull Requests. Quem não aparece documentado não tem a contribuição reconhecida.
